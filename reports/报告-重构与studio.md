## 一、先回答你问的四件事

**1）节点应该是"层状态"还是"算子"？**
两者都要，但职责不同 —— 这正是你说的 (b)(c)：

| 节点类 | 代表 | 干什么 | 端口 |
|---|---|---|---|
| **状态节点** | `x` `M[0]` `M[1]` `T[1]` `B[1]` `E[0]` `P[0]` `d[0]` `g[0]` | 一块**长期存在**的显存（生命周期 = 全程） | **左 = 写**，**右 = 读** |
| **算子节点** | `ADD` `SUB` `MUL` `SCALE` `TANH` `ONE_MINUS_SQ` `MATMUL_NN/NT/TN` | 一次计算，结果进临时区（生命周期 = 几条 op） | 左 `a` `b`，右 `d` |
| **宏节点** | `EM` | 一层推断+学习，内部展开成 9~13 个 op | 左 `g` `μ` `θ` `β` `f↑`，右 `f` `ε` `μ′` `θ′` `β′` |

**"层"不是节点，`M[l]` 才是。** `M[1]` 是 (1×1024) 的行向量，它是"第 1 层后验"，但它在图里就是一个状态节点，跟"第 0 层"的关系由连线（以及 `T[1]` 的形状绑定）决定。这样一层的层数、宽度、连接方式都只是**图的形状**，不是写死的结构。

**2）不同连线控制不同操作吗？——不。**
连线只表达两件事：**数据流** 和 **写回（别名）**。真正的"操作差异"来自节点本身和它的参数。我一开始也想用连线类型去选算子，实测下来这是个陷阱：同一根"数据线"在不同的上下文里应该产生的 op 完全不同，那你就得在 lowering 里塞一张巨大的查表，图反而成了装饰。**连线只带类型和形状，算子由节点决定**，这条守住，图才是真的。

**3）能自动生成 schedule 吗？——能，而且已经生成了。**
现在的链路是：`图(spec)` → `lower()` → `Op[]`（带相位）→ `plan()` 区间着色排偏移 → 跑 / 导出 C++。

**4）有现成模板吗？**
React Flow / Rete.js / LiteGraph.js（ComfyUI 的引擎）/ Baklava / Blockly 都能用。但我选了**手写单文件**：零依赖、`file://` 双击即开、不用 npm/打包/服务器 —— 对一个"给算法实验用的界面"，这比引入 React 生态划算。想换 React Flow 的话，`lower()` 和 `plan()` 可以原样搬走，那才是核心。

## 二、新引擎 `engine/pc.hpp`（~400 行，单头文件）

- **14 个 op**：`Clear Copy Add Sub Mul Scale Tanh OneMinusSq Clamp Matmul MatmulTA MatmulTB SumRows AddScaled`，够跑现在的模型；不够就加一个 `case`。
- **3 个相位**：`PH_PREDICT(0) → PH_INFER(1) → PH_LEARN(2)`。`run(max_phase)` 只跑到某个相位为止，所以「先推理 N 步、再学 1 步」就是 `it % N == N-1 ? run(PH_LEARN) : run(PH_INFER)`。
- **张量只有两种生命周期**：`state()` 全程常驻；`temp()` 按 `first-use / last-use` 做**区间着色**，共享一块 64B 对齐的 arena。
- **跨语言可复现的 RNG**：`seed(u32)` + `next_uniform(lo,hi) = lo + (hi-lo)·rng()/2³²`，和 JS 里的 `mt19937` 逐位一致 —— 这是"界面里看到的数 = C++ 跑出来的数"的前提。

实测规模（同一个图，只改宽度）：

| 图 | op 数 | 相位分布 | state | temp | 总计 |
|---|---|---|---|---|---|
| 2 层 D=[16,64] | 21 | 9 / 5 / 7 | 5,056 B | 8,832 B | **13.6 KB** |
| 2 层 D=[64,1024] | 21 | 9 / 5 / 7 | 272,128 B | 532,992 B | **786 KB** |
| 3 层 D=[64,512,256] | 41 | 17 / 10 / 14 | 671,488 B | 1,054,720 B | **1.69 MB** |
| 你原来手写的 2 层 | 38（13 个 CLEAR） | — | — | — | 12.32 MB |

**同样一个 2 层模型，从 12.32 MB 降到 786 KB（15.7×），op 数从 38 降到 21。**

## 三、图 → schedule 怎么落（关键语义）

### 3.1 一条规则概括：**状态的左端口是"写"，右端口是"读"**

```
   M[1] ──[μ 读]──────────► EM[1].μ        读 = 状态节点右侧出线
   EM[1].μ′ ──[写回]──────► M[1].写         写 = 算子输出接状态节点左侧
```

- 算子 `d` 接到状态的 `in` ⇒ 这个算子**原地写**那块状态（`M[1] += η·Δμ` 就是 `AXPY(Δμ, η) → M[1].in`）。
- 状态 `read` 接到算子输入 ⇒ 只读。
- **纯数据线是细蓝实线，写回线是虚线** —— 一眼能看出"这块内存被谁改了"。这就是你说的"不同类型的连线"，但它控制的是**别名**，不是算子。

### 3.2 EM 宏展开（一层，d=1）

```
f₁ = tanh(μ₁·θ₁ + β₁)                     ← MATMUL_NN, ADD, TANH
ε₁ = μ₁ − f₁                              ← SUB（或 ω·μ₁，顶层）
μ₁′ = μ₁ + η_μ(g₀·θ₁ᵀ − ε₁)               ← MATMUL_NT, SUB, AXPY       [推理相位]
θ₁′ = θ₁ + η_θ·μ₁ᵀg₀                       ← MATMUL_TN, AXPY            [学习相位]
β₁′ = β₁ + η_β·g₀                          ← AXPY                        [学习相位]
```

`μ/θ/β` 三个量都**不原地改**，而是产出 `μ′/θ′/β′`，再由写回线拷回去。好处：一个宏节点在图上只有一组"读端口 + 写端口"，和你手画的那张草图完全对应。

### 3.3 顶层先验 ω（**这是我修掉的一个塌缩**）

顶层的误差项不能是 `ε = μ`（等价于先验 N(0,I)），否则自由能里 `‖μ‖²` 那一项会把高阶后验一路压到 0：`μ→0 ⇒ θ 的驱动项 μᵀg→0 ⇒ θ→0 ⇒ 只剩 β 在拟合`。实测（D=[64,1024]，固定样本 2000 步，每元素平均 `e₀`）：

| 顶层精度 ω | 平均 e₀（第 2000 步） | ‖M[1]‖ |
|---|---|---|
| 1.0 | 0.0141（还在涨） | 1.0（塌缩中） |
| 0.3 | 0.0027 | 2.5 |
| 0.1 | 0.0013 | 5.2 |
| **0.02（默认）** | **0.0002** | **6.3** |
| 0.01 | 0.0002 | 12.4（过大） |

所以默认 `ω=0.02`：`ε_top = ω·μ_top`。界面上是「顶层先验 ω」这个输入框。

## 四、`pc-studio.html`：你要的组件库 + Run

单文件、零依赖，双击打开。

- **左侧组件库**：按 `状态 / 算子 / 集成` 分组，**点击**加到画布中央，**拖拽**放到指定位置。
- **画布**：拖节点、拖背景平移、滚轮缩放；从端口拖线（左出→右入），点线删除，Delete 删节点。
- **右侧运行面板**：`运行 ▶ / 单步 / 重置`，速度、已跑步数、**自由能 F**、`‖ε₀‖²`、F 曲线（对数轴，最近 240 步）、当前样本热力图、检视器（选中节点看形状/偏移/产生的 op）。
- **顶部**：三个预设（2 层 / 3 层 / 只有输入层）、`整理布局`、`导出 JSON`、`导出 C++`、`帮助`；右边常驻 **ops/step、arena、校验** 三个徽章。
- **超参**：`η_μ` `η_θ` `η_β`、每 N 步学一次、种子、**顶层 ω**、固定样本开关、层宽 D。改任何超参都会重新 lower + 重新初始化（`nInfer` 除外，它只改节拍）。
- **深链**：`pc-studio.html#run=2000` 打开就跑 2000 步，`#deep` / `#single` 选预设 —— 方便截图和写文档。

**实测（2 层 64→1024，固定样本，2000 步）**：`‖ε₀‖²` 从 15.58 降到 0.0158（**985×**），F 3.75 → 0.0188；`‖M[1]‖²=7.44`、`‖T[1]‖²=217.7`、`‖B[1]‖²=0.16` —— 高阶表征是活的，不是靠偏置糊弄。3 层 64→512→256 跑 600 步 F=0.0368。

## 五、"界面里的数 = 导出的 C++ 的数"（这是最重要的验收）

`导出 C++` 不是模板拼字符串：它是**从已经 plan 好的那个 Program 里逐个 op 生成**的，所以不可能和图不一致。

- `examples/pc_basic.cpp` 用 `gen/model.hpp` 跑 2000 步；`tool/dump_js.js` 在 node 里跑同一个图，两边逐行对比：

## 六、过程中抓到的 6 个真 bug（按杀伤力排序）

1. **`rebuild()` 里重新 `lower()` 了一次** —— 等于每次画完就把训练好的状态清零。现象：`M[1]`、`T[1]` 恒等于 0，只有 `β` 在学，F 还能"下降"（因为它只降 `‖x−tanh(β)‖`）。这是那种"曲线好看但模型是死的"的典型，**必须靠打印中间张量才能发现**。修法：`rebuild()` 只画图，lower+init 只在 `resetRun()` 里做。
2. **写回线的查找方向错了** —— 早先按"进 `n.d` 的边"找，但输出端口没有入边，于是所有写回都悄悄退回成临时 buffer。正确写法是找**从 `n.id.d` 出去的边**。
3. **μ 更新符号反了** —— 写成 `μ += η(gθᵀ − ε)` 之前先试过 `−lrMu`，那会让 `ε=μ` 变成正反馈，F 从 0.23 涨到 1.5e33（400 步内）。正确：`μ += η(gθᵀ − ε)`。
4. **`x → M[0]` 被"写回规则"跳过** —— 状态→状态的拷贝被当成"不需要"，于是 M[0] 从来不是输入。修法：只跳过自身拷贝（`src.id === dst.id`）。
5. **导出 C++ 时 `acc` 参数没显式传** —— `pr.mmtb(a,b,d, pc::PH_INFER)` 把相位实参喂进了 `bool acc`（隐式转换），于是推理用的 gemm 变成累加、相位也错。这就是"JS 和 C++ 从第 2 步开始分叉"的根因。
6. **数据流多抽了一次** —— C++ 的 `Stream` 构造函数里多调了一次 `next()`，导致第一个样本被跳过。现象：第 0 步一致、第 1 步开始偏。

这 6 个都属于**静默错误**：不崩、不报错，只是数不对。所以 `tool/verify` 式的一次性对比是必须的 —— 这也是"自研前端"最该先建的东西：**数字回归**，不是界面。

## 八、下一步（按性价比）

1. **给 op 加反向/伴生**：现在是手推的更新规则（`μ′/θ′/β′`），下一步可以让 `EM` 宏内部改由一次 `backward` 生成，这样新算法只要写前向。
2. **权重共享 / 多连接**：`T[1]` 已经能在多个 EM 之间共享（同一个状态节点接两条读线即可），可以加一个"绑定"标记让 `T[l]` 在层间复用。
3. **稀疏/低秩**：`T` 的 op 只有 `MATMUL_*`，加 `LOWRANK` / `SPARSE` 两个 op 就能试 LoRA 式的更新。
4. **批次**：现在全是 1×D 的行向量（和你定的"后验是行向量"一致），批量化只要把 `M[l]` 变成 (B,D[l])，`SUM_ROWS`/`Matmul` 都兼容。
5. **性能**：786 KB arena、21 op/步，现在的瓶颈是 `cblas_sgemm` 的调用开销（1×1024×64 太小），可以攒批或换手写 kernel —— 但这属于"不该自研"的那一栏，先别动。

**一句话**：界面现在能搭、能跑、能导出、能和 C++ 对上数；下一步该往算法里加"新 op / 新宏"，而不是继续堆界面。

## 九、后续改动（v1.0.1 起）

- **删掉 `spec.dims`**：层的宽度过去是全局数组 `dims`，所有状态形状从它推。现在每个状态节点自带 `shape`，
  形状校验发生在算子连上来的时候（报错文案带实际形状，例如 `矩阵乘不上: 1×8·6×4（左列 8 ≠ 右行 6）`）。
  同一张图里因此可以有任意宽度、任意分支。老图里的 `dims` 被忽略，缺 `shape` 的节点按 `θ → 64×64`、其余 `→ 1×64` 兜底。
- **连带删掉的死参数**：`spec.v`（版本号留在文件外壳 `{ v, name, spec }`）、导出 C++ 里的 `NL` / `D[]`
  常量（`examples/pc_basic.cpp` 改为从模型里查名为 `x` 的状态张量拿输入宽度）、`portShape` 里永远走不到的
  `def.shape(D, n.l, n)` 分支、`ctx.D` / `ctx.L`。
- **端口按接线状态着色**：蓝=数据线、黄=写回线（`to` 落在状态 `in` 上）、红=必需但没连（算子的 `a`/`b`、
  EM 的 `μ`/`θ`）、灰=没连但不必需（状态端口、监视、可选输入、没连线的输出）。输出端口跟随它连出去的那根线
  （接状态「写」口→黄），所以 EM 右侧五个黄虚线输出会显示成黄点。必需性写在 `library.js` 的端口上
  （`optional: true` 表示不必需），所以加新组件时顺手声明即可。

  实现细节：`geom()` 把端口归一化成 `{ k, name, optional }`，`render.js` 的 `pinState(n, p, dir)` 只认这一个字段
  —— 之前 `geom()` 写的是 `opt`、`pinState()` 读的是 `optional`，输入端口因此全部被误判成"必需"（EM 的
  `f_l（上层预测）` 明明可选却标红）。

- **连线有向化（v1.0.2 起）**：原来用「蓝实线 / 黄虚线」区分数据线和写回线，含义不自明——同一根线上看不出哪头是源。
  现在改成：一条线在中点附近**从源端口色过渡到目标端口色**，端口颜色同时简化成纯语义：蓝 = 算/读出来的值，
  黄 = 会落进一块状态缓冲区的新值。于是「蓝→黄 = 算完存起来」「蓝→蓝 = 只是读去参与运算」「黄→黄 = 写回链」
  三句话就能读完整个画布。
  实现上 `wires.js` 为每条边生成一个 `linearGradient`（`gradientUnits="userSpaceOnUse"`，四个 stop：
  `0 / 0.42 / 0.58 / 1`），中间这 16% 是过渡带——既不是生硬的硬切，也不会像连续插值那样在蓝黄之间拖出一段发灰的
  过渡。早期版本在终点画过三角形箭头，后来去掉了：箭头在细线上容易糊成一团，而颜色本身已经指明方向。
- **端口颜色改为"方向驱动 + 接线后才上色"（v1.0.4 起）**：接线后蓝 = 输入口（组件左边）、黄 = 输出口（组件右边）；
  没接的非必需口不着色（灰环 + 黑心），没接的必需口标红。连接点画成「半圆环 + 同心小圆」，小圆比环暗一档，
  所以"接没接"和"往哪流"是两套互不干扰的视觉编码（前者看填充，后者看环色）。
  颜色与"这个口是谁"、与接线状态都无关，因此每个组件的每个连接点都有确定颜色；"连没连"改用**实心/空心**表达。
  于是每条连线天然是"黄 → 蓝"，方向不再需要箭头。途中试过"按读/写语义上色"（EM 右侧全黄、状态写口黄），
  但用户最终约定按方向，语义配色被替换掉——`library.js` 里的 `write` 标记随之删除，避免两套规则并存。
  自检里保留一条覆盖率审计：`pin-audit total 62 in 32 out 28 need 2 open 6 uncolored 0`，保证没有"没颜色"的端口。
- **EM 右侧整排都是黄色（v1.0.3 起）**：`f` / `ε` 一开始被当成"算出来的值"标成蓝，但它们在语义上同样是**要落到状态里
  的新值**（写回上层、或落进下层的 `P`/`E`），于是五个输出统一在 `library.js` 里标了 `write: true`。这样"EM 右边是
  写、左边是读"就是一条能直接看出来的规则，不需要记特例。
